# 性能与流畅度

## 本机流畅度检测

在“设置 → 外观与动效 → 流畅度检测”开始 20 秒检测，返回书架或阅读器，重复开书、滚动、切页，再回到检测页查看或复制结果。也可提前结束；切到后台会停止记录。

检测只保留本次 Flutter 准备与绘制画面的耗时，最多 4800 个样本，不记录标题、网址、图片或设备标识，不上传数据。首批可能包含检测前的画面，因此不计入。P95 是耗时分布的第 95 百分位；超过帧预算的数量按准备或绘制阶段分别与参考刷新率比较，不将流水线重叠阶段相加。刷新率可能随系统策略变化，结果不是屏幕实际 FPS、功耗或发热结论。浏览器可能不提供此类样本。

建议用 Android Release 包，在同一设备、亮度、刷新率与网络条件下分别检查冷启动后的首次操作和重复操作。大图解码、在线请求、玻璃效果与纯手势路径分别记录，避免把网络等待当作绘制卡顿。

## 当前资源控制

- 阅读预载只运行一个任务；新窗口替换未开始的旧任务，已开始的解码允许完成。停止阅读后不启动后续任务。
- 预载按方向准备图片，失败不会永久占用去重记录；缓存键包含清晰度，完成记录最多保留 12 项。
- 保存页码不重建全局主题与导航配置。语言、主题、插件和可读性设置仍即时生效。
- 标准材质和高对比度面板跳过背景滤镜；标准材质不预先创建玻璃着色器。

这些改动限制额外工作量，不等于已经通过所有设备的流畅度验收。物理 iQOO 的帧耗时、发热和安装体验仍需实际检测。

## 2026-10-30 Web 渲染测量

Web 构建启用 `--wasm`，预览服务提供 COOP/COEP 隔离响应头，使 skwasm 使用渲染工作线程；构建同时保留 JavaScript/CanvasKit 回退。可查看 [Flutter WebAssembly 文档](https://docs.flutter.dev/platform-integration/web/wasm)。Android 渲染器不受此改动影响。

同一桌面 Chromium headless、390 × 844、标准材质、五本测试收藏及相同书架操作，分别确认加载 `main.dart.js/canvaskit.wasm` 和 `main.dart.wasm/skwasm.wasm`；后者确认 `crossOriginIsolated=true`。每次使用独立上下文，统计主线程 `BeginMainFrame`，包含 tracing 开销：

| 渲染路径 | 样本 | P50 / ms | P95 / ms | 最大 / ms | 超过 50 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 同次 Web 构建的 CanvasKit 回退 | 161 | 21.547 | 39.398 | 128.268 | 7 |
| skwasm 工作线程 | 220 | 2.638 | 4.609 | 17.695 | 0 |
| skwasm 工作线程重复检查 | 222 | 2.709 | 4.350 | 17.968 | 0 |

书架工作线程两次检查均通过主线程 P95 ≤ 16.67 ms、无超过 50 ms 长帧的检查。该改动将渲染工作移出主线程，这组数字不能代表 GPU、工作线程自身或显示帧率已经达标，也不能换算为 Android FPS 提升。

另按场景记录：发现页进入、滚动及追更筛选首次 120 个样本，P95 9.116 ms、最大 51.795 ms，有 1 个超过 50 ms 的样本，未通过严格长帧检查；复测 121 个样本，P95 9.093 ms、最大 49.220 ms，无超过 50 ms 的样本。真实在线阅读进度跳转与跨章 125 个样本，P95 6.443 ms、最大 12.758 ms，无超过 50 ms 的样本。发现页使用固定目录响应；在线阅读通过本机网关读取来源及图片。这些不是前后对照，不据此宣称消除了所有卡顿。测量记录仅保存在本机 `.qa`，不包含在项目发行中。

实际 Android/iQOO 的长时间阅读、温度、触感与帧率仍需物理设备验证。原有本机流畅度检测入口继续保留，可在设备上分别记录书架、发现和阅读流程。

## 0.2.2 历史优化与验收

## 已调整的路径

- 书籍的封面底图、书脊和文字录制成 ui.Picture；动画复用绘制命令，只改变几何投影、动态光照和位置。内容、序号、书签或封面变化时才重建；组件销毁时释放资源。
- 书籍封面最大按 512 像素宽解码；漫画正文不受这个封面限制影响。相同封面的读取不再跟随布局依赖重复发生。
- 封面取色在 32 × 32 缩略图上读取像素，缓存最多 48 个颜色结果。缓存不保留图片句柄；采样使用的临时图片和画布会释放。
- 只有访问过的页面才创建，切走后保留其场景与选书位置，停止不可见页的 tick/绘制。发现页换源时使用新状态，避免保留旧来源结果。
- 当前页由 RepaintBoundary 隔离，切页使用平移与淡入，不再对整页做变化中的模糊。
- 高级设置分组通过 SliverList 按滚动位置创建，首次打开不再一次性布局整页选项。
- 底栏保留真实背景模糊；玻璃底板与移动的选中块分层，镜片动画不再每帧重建和缩放整个滤镜。
- 大幅模糊封面背景改为封面取色后的柔和色场，保留环境色过渡；正文滚动仍会透过底栏的真实毛玻璃。
- Android 测试包改用 Profile/AOT；开发调试可运行 tools/Build-Android.ps1 -Debug，正式签名发行使用 -Release。Profile 不等于真机帧率已通过。

## 测量方法

本机浏览器 release 构建、390 × 844 逻辑视口，辅助语义开启，封面资源已加载。连续点四次“下一本”，每次留 600 ms；进入设置并返回书架，各留 700 ms。Chrome tracing 记录渲染器主线程 BeginMainFrame 时长。

初始 0.2.1：P50 7.567 ms、P95 17.299 ms、最大 80.853 ms；348 个主线程帧工作样本，21 个超过 16.67 ms，2 个超过 50 ms。

最终提交 f1de1b0 的测量结果：

| 场景 | P50 / ms | P95 / ms | 最大 / ms | 超过 50 ms |
|---|---:|---:|---:|---:|
| 0.2.1 初次进入设置 | 7.567 | 17.299 | 80.853 | 2 |
| 0.2.2 初次进入设置 | 6.808 | 12.204 | 59.560 | 1 |
| 0.2.2 已访问页面后重复 | 6.188 | 10.780 | 26.107 | 0 |

初次设置场景仍未通过严格的 50 ms 长帧检查，不能宣称已完全消除卡顿；保留这个失败结果。已访问页面后的重复操作通过检查。前两行是相同冷访问流程；第三行单独列出热状态，不拿它和第一行计算提升比例。不同采样次数受调度影响，不将帧数量直接换算为 FPS。

复核工具：python tools/analyze-performance.py .qa/perf-before.json --check。原始 trace 保存在本机 .qa，不提交浏览器记录。--check 按 P95 不超过 16.67 ms、没有超过 50 ms 的主线程帧工作做检查。

这些是当前机器与固定交互下的浏览器主线程测量，包含 tracing 开销；它们不能替代 GPU 呈现帧率、Android 真机、滚动长漫画或不同档位设备的测试。保留前后原始结果，不能把不同配置的数字混成一个 FPS 提升比例。
